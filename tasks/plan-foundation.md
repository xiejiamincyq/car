# Neon Coast Rush 完成度加固与内容闭环计划（0.1.0-rc.1 → 0.2.0）

## 1. 计划结论与目标

当前版本应定义为“核心循环可玩的纵向切片”，还不宜视为真正的发布候选。现有驾驶、交通、燃油和计分系统已经构成技术基础，但缺少正式界面流、持久化、明确赛段目标、中后期内容变化、平台行为验证和足量人工试玩，因此玩家仍会明显感到它是半成品。

本计划的目标是在不依赖新美术和背景音乐的前提下，先完成两个层次：

1. **核心完成路径：** 从标题界面开始，玩家能够理解目标，完成一场有起点、赛段变化、终点和结算的比赛，并可稳定重玩。
2. **增强路径：** 补齐手柄/改键、双语、可访问性和程序化音频，使游戏更接近正式 PC 小品游戏。

进入原创美术集成前，必须先通过“核心完成检查点”。增强路径可根据试玩反馈决定是否全部纳入 0.2.0，不再阻塞核心内容闭环。

## 2. 范围与原则

### 2.1 硬约束

- 不新增精灵图、贴图、外部字体和背景音乐；现阶段继续使用 `_draw()` 几何绘制、现有菜单背景和程序化音效。
- 不破坏确定性；影响交通、事件和计分的改动必须提供固定种子测试。
- 每个任务完成后运行对应测试；每个大阶段结束运行全套 `tests/test_*.gd`。
- 优先级固定为：操控手感与公平性 > 一局完整性 > 内容变化 > 包装与扩展能力。
- 新机制必须有独立开关或集中配置，出现回归时可以快速隔离。
- 不以“功能已经写入代码”为完成标准，必须同时通过自动测试、Windows 构建冒烟和人工试玩。

### 2.2 本计划不做

- 原创车辆、道路、场景、字体、图标和 BGM 的制作与集成。
- 联网排行榜、账号、云存档、多人模式、Web 导出。
- 大规模关卡编辑器或剧情系统。
- 对 Road Fighter 的受版权保护素材做直接复制；只复刻其俯视驾驶、交通闪避、燃油压力、阶段推进和街机节奏。

## 4. 目标玩法闭环

0.2.0 的核心模式采用“有限赛程 + 通关后可选无尽”的结构：

1. 玩家从标题界面选择难度并进入比赛。
2. 一局划分为 4 个可配置赛段；赛段以距离或进度阈值推进，具体数值在 F7 用试玩数据确定。
3. 通过检查点时给予少量燃油补给，并明确显示赛段变化；后续赛段逐步引入货车和封路事件。
4. 通过最终检查点触发 `RUN_CLEAR`，进入正式结算，而不是只能以燃油耗尽结束。
5. 通关后可选择“继续冲分”进入无尽模式，或返回标题/重新开始。

这样既保留 Road Fighter 式的持续压力，也给普通玩家一个清楚、可实现的短期目标。若 F3B 试玩证明无尽模式会稀释通关感，可将其延期，不影响核心验收。

- 提供键位捕获、冲突提示、恢复默认和持久化。
- 输入提示根据最后使用设备切换；没有原创图标时使用文字。

**验收与验证：**

- [ ] 纯手柄完成标题到结算全流程。
- [ ] 改键、冲突处理、恢复默认和重启保留测试通过。

**依赖：** F1、F2。若 0.2.0 只承诺 PC 键盘试玩，本阶段不阻塞发布。

---

### F5：双语与可访问性（2–3 天，增强）

**目标：** 清除写死文案，并提供低成本、高价值的可访问性选项。

#### F5.1 文案集中与中英双语（M）

- 全部 UI 字符串集中管理，两套语言键集合必须一致。
- 默认跟随系统语言，允许设置中切换并持久化。

#### F5.2 视觉反馈选项（M）

- 提供高对比/色弱友好配色、震动开关、闪烁关闭或降频。
- 危险、燃油和车辆类型不能只靠颜色区分。

**验收与验证：**

- [ ] 缺键测试、切换和持久化测试通过。
- [ ] 两种语言逐界面人工检查，无截断和混杂。

**依赖：** F1、F2、F3A。

---

### F6：程序化音频完善（1.5–2 天，增强）

**目标：** 在不引入音乐资源的情况下，让操作、危险和奖励具有清楚的听觉层次。

- 增加 UI 移动/确认/取消、近失、连击、倒计时、检查点、通关、低燃油和封路预警音。
- 建立 `Master`、`Effects` 和预留 `Music` 总线；设置提供主音量和静音。
- 保持引擎音随速度变化，并避免多音效叠加削波。

**验收与验证：**

- [ ] 每种音效可生成，采样长度合理，无 NaN 和明显截幅。
- [ ] 静音和 0% 音量时无声音泄漏。
- [ ] 玩家可仅凭声音区分碰撞、近失、检查点和低燃油。

**依赖：** F1、F3A、F3B。

### 检查点 D：增强范围决策

- [ ] 根据检查点 C 反馈决定 F4B、F5、F6 哪些进入 0.2.0。
- [ ] 若核心完成感仍不足，增强阶段暂停，时间回投 F3B。
- [ ] 只有共享接口冻结后，互不修改同一文件的增强任务才可并行。

---

### F7：平衡、发布验证与美术交接（3–4 天，核心）

**目标：** 用真实试玩数据收敛参数，产出可复验的 Windows 0.2.0 候选包。

#### F7.1 三人平衡试玩（M）

- 至少 3 名试玩者覆盖轻松、标准、困难。
- 记录首局目标理解、通关率、局长、死亡原因、不可避免碰撞、完成感和重玩意愿。
- 每轮只调整少量集中配置参数，并记录前后数据。

**验收与验证：**

- [ ] 标准难度首批试玩通关率处于可接受区间；最终目标值由首轮数据确认并写入发布清单。
- [ ] 高频反馈均有修复、验证或明确延期理由。

#### F7.2 全量回归和 Windows 冒烟（M）

- 运行全套自动测试、20 种子压力模拟和难度组合抽查。
- 在干净用户目录验证首启、存档、全屏、失焦、通关、失败、重开和退出。

**验收与验证：**

- [ ] 自动测试零失败，无确定性漂移。
- [ ] Windows 包至少在目标开发机和 1 台非开发机完成冒烟。

#### F7.3 版本与美术交接（M）

- 更新版本号、导出元数据、README、CHANGELOG、发布清单和任务状态。
- 输出美术需求清单：替换点、尺寸、锚点、碰撞边界、动画状态、配色语义及文件命名。
- 规则、状态机、存档格式和输入动作冻结；后续美术替换不得隐式改变碰撞和玩法。

**验收与验证：**

- [ ] `exports/` 产生可启动的 0.2.0 候选包。
- [ ] 美术人员无需阅读玩法代码即可理解所需资产和接入约束。

**依赖：** F0–F3B、F4A；F4B/F5/F6 仅在检查点 D 决定纳入时成为依赖。

## 6. 排期与模型建议

以下为 1 名开发者配合 AI、包含测试修复和人工验收缓冲的现实估算。

| 阶段 | 预计用时 | 路径 | 推荐模型/工具 | 适合工作 |
|---|---:|---|---|---|
| F0 | 1–1.5 天 | 核心 | Terra | 文档对齐、脚本检查、导出配置 |
| F1 | 4–5 天 | 核心 | Sol | 状态机、复杂 UI 流、回归分析 |
| F2 | 1.5–2 天 | 核心 | Terra，关键容错由 Sol 复核 | 存档实现与测试 |
| F3A | 3–4 天 | 核心 | Sol | 近失、连击、反馈和确定性测试 |
| F3B | 5–7 天 | 核心 | Sol | 赛段、事件、公平性和压力模拟 |
| F4A | 1.5–2 天 | 核心 | Terra | Windows 平台行为与适配 |
| F4B | 2.5–4 天 | 增强 | Sol | 输入抽象、手柄、重绑冲突 |
| F5 | 2–3 天 | 增强 | Terra | 文案集中、设置与布局检查 |
| F6 | 1.5–2 天 | 增强 | Terra；需要音效风格探索时可用 Sol | 程序化音频和混音 |
| F7 | 3–4 天 | 核心 | Sol 负责回归诊断，Terra 负责文档与机械收尾 | 平衡、发布验证、交接 |
| 原创美术阶段 | 另行计划 | 后续 | 图像模型 + Sol 集成复核 | 概念图、精灵、背景、UI 资产 |

**总工期：**

- 核心完成路径（F0、F1、F2、F3A、F3B、F4A、F7）：约 **19–25.5 个工作日**。
- 增强路径（F4B、F5、F6）：增加约 **6–9 个工作日**。
- 全部纳入：约 **25–34.5 个工作日**。若有稳定并行能力且共享接口已冻结，可压缩到约 **22–31 个工作日**。

模型选择是执行建议，不是质量门槛。每个大阶段仍应由当前主任务统一上下文，并在阶段结束接受人工试玩或重大决策；图像模型只在原创美术阶段使用，不应用来掩盖核心玩法未闭环的问题。

## 7. 依赖关系与停止条件

```text
F0 → F1 → F2 → F3A → F3B → F4A → F7 → 原创美术集成
                 └──────────────┬──────────────┘
                                ├→ F4B（可选）
                                ├→ F5（可选）
                                └→ F6（可选）
```

执行时仅在以下情况停止并请求人工处理：

1. 完成检查点 A、B、C、D 或 F7，需要人工试玩和签字。
2. 试玩反馈要求改变核心模式、赛段数量、胜利条件或输入平台范围。
3. Windows 导出模板、目标设备或外部依赖阻塞，无法通过安全的本地修复继续。
4. 任何阶段超过估算上限 50%，需要决定砍范围还是延长排期。

邮件提醒和自动打开试玩界面属于执行流程，不属于游戏代码的完成条件。到达人工试玩检查点时，若邮件连接器可用则发送提醒，并在获得系统权限后启动最新 Windows 构建；若连接器不可用，应在任务中明确通知用户，不得伪称已发邮件。

## 8. 0.2.0 核心完成定义（Definition of Done）

- [ ] 玩家可从标题开始，在无需调试工具和口头说明的情况下完成或失败一局、查看结算并重玩。
- [ ] 至少有 4 个可感知赛段、检查点反馈和明确 `RUN_CLEAR` 终点。
- [ ] 中后期至少包含一种新交通约束和一种路况事件，且固定种子公平性回归通过。
- [ ] 成绩、设置和关键统计跨进程保存；损坏存档不会阻止启动。
- [ ] PC 键盘全流程、全屏、失焦暂停和恢复倒计时在 Windows 包中通过冒烟。
- [ ] 全套自动测试零失败，压力模拟无对象泄漏、死锁或确定性漂移。
- [ ] 至少 3 名试玩者完成记录；关键理解度和公平性问题已关闭或明确延期。
- [ ] README、CHANGELOG、发布清单、版本号和美术需求清单与实现一致。

F4B、F5、F6 只有在检查点 D 被正式纳入 0.2.0 时，才加入本版本 DoD。

## 9. 主要风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 新赛段、货车和封路叠加后产生无解局面 | 高 | 独立开关；先单机制测试，再组合压力模拟；保留最小反应时间和逃生路线不变量 |
| 状态机改造波及已稳定驾驶循环 | 高 | 先冻结状态契约；每个界面纵切后跑核心回归；不在 F1 改交通物理 |
| 录制演示随规则变化漂移 | 中 | 首选预定义控制器；录制输入必须版本化并在规则变化后重录 |
| 存档替换在异常退出时失败 | 中 | 旧文件/默认值可恢复；写入失败只告警；测试恢复行为，不承诺跨平台严格原子性 |
| 连击令高风险贴车成为唯一最优策略 | 中 | 以得分分布和试玩死亡原因为依据调整倍率、窗口和奖励 |
| 手柄、双语等增强项拖延核心完成 | 高 | F4B/F5/F6 不阻塞核心路径；检查点 D 决定是否纳入 |
| 只增加包装仍被评价为半成品 | 高 | 检查点 C 以胜利条件理解度和完成感为硬门槛，失败则回投 F3B |
| 工期被低估 | 中 | 使用 19–25.5 天核心估算；阶段超期 50% 时触发范围决策，不静默透支 |

## 10. 进入原创美术阶段的批准条件

- [ ] 核心 DoD 全部通过，检查点 C 与 F7 人工验收完成。
- [ ] 0.2.0 Windows 候选包已在非开发机冒烟。
- [ ] 游戏规则、状态机、输入动作、存档结构和碰撞边界冻结。
- [ ] 美术需求清单已评审，明确哪些几何绘制将被替换、哪些反馈语义不得改变。
- [ ] 尚未完成的增强项已明确放入后续版本，不再与美术阶段混在一起执行。
