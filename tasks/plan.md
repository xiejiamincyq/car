# Neon Coast Rush 初始 MVP 实施计划（PC 键盘试玩版）

> 本文记录 0.1.0-rc.1 纵向切片的历史实施范围。该版本已经建立驾驶、交通、燃油、计分和自动回归基础，但不代表完成品；当前完成度加固工作以 [`plan-foundation.md`](plan-foundation.md) 为准。

## 1. 项目概览

目标是在 **12–16 个有效工作日（约 60–88 小时）** 内完成一个可供小范围试玩的原创 2D 街机赛车 MVP。时间按 1 名开发者、已有 Godot 4 环境、使用 AI 辅助编码估算；首次接触 Godot 或美术资源需额外预留 20–30%。

开发优先级始终是：**操控手感 > 车流公平性 > 一局完整性 > 视觉包装**。任何阶段如果核心体验未通过验收，先调整再推进，不用美术掩盖问题。

## 2. 模型使用建议

| 场景 | 推荐模型 | 原因与使用方式 |
|---|---|---|
| 常规 Godot/GDScript 实现、UI、文档、测试 | GPT-5.6-Terra | 平衡速度与质量，适合大多数中小型任务；每次只提交一个可运行的小切片。 |
| 游戏状态机、交通生成、疑难 Bug、性能与测试审查 | GPT-5.6-Sol（高推理） | 用在高风险逻辑和定位异常，先要求给出根因、边界条件和验证步骤。 |
| 原创占位图、菜单背景、概念氛围图 | 图像生成模型 | 仅生成原创资源；不上传或要求仿制《Road Fighter》素材。先用色块验证玩法，最后再生成。 |

**协作准则：** Terra 负责实现 → 本地运行验证 → Sol 审查高风险逻辑或失败测试 → 人工试玩决定手感参数。模型给出的任何数值、Godot API 与导出配置都必须在本地验证。

## 3. 系统依赖关系

```text
输入映射 + 游戏窗口
        ↓
玩家控制 + 道路滚动
        ↓
交通生成与回收 ──→ 碰撞与反馈
        ↓                   ↓
燃油/分数/难度状态 ───────→ HUD
        ↓
开始 / 暂停 / 结束 / 重开
        ↓
试玩调参 + 自动检查 + Windows 导出
```

## 4. 分阶段计划

### 阶段 0：立项与可玩性基线

**预计用时：** 0.5–1 天（3–6 小时）\\
**推荐模型：** GPT-5.6-Terra；关键规则由 GPT-5.6-Sol 复核\\
**目标：** 把“参考作品的玩法原则”转译为自己的可测规则，而不是复制内容。

**任务：**

1. 确认 Godot 4 版本、Git 仓库、Windows 导出模板与项目目录规范。
2. 定义原创主题、车辆命名、道路美术方向与可接受的参考边界。
3. 建立 8–12 个可调参数：最大速度、加速度、横移速度、路宽、出生距离、最小安全间距、碰撞惩罚、燃油消耗/补充量。
4. 写一页试玩记录模板：时间、死亡原因、存活时长、主观公平性（1–5）。

**验收标准：**

- [ ] 项目能在 Godot 中打开，Windows 导出模板可用。
- [ ] 核心参数集中配置，而非散落在脚本常量中。
- [ ] 明确不会使用任何参考游戏的原始资源或关卡数据。

**依赖：** 无。

### 阶段 1：60 秒驾驶原型

**预计用时：** 1.5–2 天（10–14 小时）\\
**推荐模型：** GPT-5.6-Terra 实现；GPT-5.6-Sol 审查操控边界\\
**目标：** 没有敌车也能感到“车在高速前进”，且键盘操控可信。

**任务：**

1. 创建 16:9 主场景和输入映射：方向键/WASD、Esc、R。
2. 实现玩家车的横向转向、加速、减速、速度上限和道路边界。
3. 用道路标线/路肩循环制造纵向卷轴；速度变化必须影响视觉速度。
4. 加入开发 HUD：当前速度、横向位置、帧率和当前调参值。

**验收标准：**

- [ ] 连续驾驶 60 秒无输入丢失、穿模或越界。
- [ ] 低速精确、高速紧张，但玩家仍能在一个车道宽度内修正。
- [ ] 松开方向键后车辆横向行为符合选定设计（快速回正或惯性滑行），并在试玩记录中确认。

**验证：** 左右各持续按住 10 秒、零到最高速再降至零各三次；录屏复查路面滚动与车体位置。

**依赖：** 阶段 0。

### 检查点 A：操控批准

- [ ] 至少 1 名非开发者可以在 30 秒内理解加速、转向、边界。
- [ ] 若“高速下无法稳定换道”或“速度感不明显”，回到阶段 1 调参。

### 阶段 2：交通、风险与公平碰撞

**预计用时：** 2.5–3.5 天（16–22 小时）\\
**推荐模型：** GPT-5.6-Terra 拆分实现；GPT-5.6-Sol 负责生成规则/碰撞审查\\
**目标：** 玩家开始做超车决策，但从不因屏外突发或重叠出生而无解。

**任务：**

1. 建立对象池与可设置随机种子的交通生成器；交通只在屏幕上方安全距离外出生。
2. 实现三种原创交通行为：慢速稳态、预示后变道、快速追越；先以确定性规则实现。
3. 实现玩家与交通的碰撞：速度损失、短暂无敌、闪烁、镜头震动、占位音效。
4. 加入“出生安全验证”：同车道最小间距、相邻车道可避让、玩家当前速度下的反应时间阈值。

**验收标准：**

- [ ] 固定种子重开两次，前 30 秒交通顺序相同。
- [ ] 十次随机开局中前 15 秒无不可避免碰撞。
- [ ] 一次碰撞只结算一次惩罚，无敌结束后不会立刻被相同车辆重复击中。

**验证：** 运行 5 分钟压力测试，记录活跃车辆数量；以 3 个种子分别测试低、中、高速碰撞。

**依赖：** 阶段 1。

### 检查点 B：核心乐趣批准

- [ ] 试玩者能说出至少一种交通行为的区别。
- [ ] 试玩者认为失败主要源于自己的判断，而不是生成系统“不讲道理”。
- [ ] 如未通过，优先降低密度、拉长出生距离、增加变道预告；不增加更多车种。

### 阶段 3：燃油、得分与完整单局

**预计用时：** 2–3 天（12–18 小时）\\
**推荐模型：** GPT-5.6-Terra；状态边界和重置测试交给 GPT-5.6-Sol 复核\\
**目标：** 让玩家拥有明确的长期压力、结束条件和即时重试动机。

**任务：**

1. 新增 `RunState`：运行中/暂停/结算状态、距离、分数、燃油、难度阶段。
2. 实现燃油衰减、原创燃油补给物、补给判定和燃油耗尽结束。
3. 实现距离基础分、超车奖励和可选的近距离擦车奖励（若影响公平性则延后）。
4. 建立逐段难度曲线：先提高交通密度，再引入更大速度差，最后增加变道频率。
5. 完成开始、暂停、结束、结算和 R 键重开；重开必须清除旧节点和旧状态。

**验收标准：**

- [ ] 燃油、分数、距离和暂停状态在 HUD 中实时且正确显示。
- [ ] 燃油归零、碰撞规则和重开流程均能回到干净的新局。
- [ ] 一局平均时长落在 2–4 分钟目标附近；首 30 秒不因燃油压力结束。

**验证：** 连续完成 10 局，覆盖暂停、燃油耗尽、碰撞、捡补给和重开；检查重开前后活跃节点和数值。

**依赖：** 阶段 2。

### 检查点 C：MVP 功能完成

- [ ] 从启动到结算再到重开不需要重启程序。
- [ ] 三名试玩者的死亡原因有记录，并据此只调整最影响公平性的 1–3 个参数。

### 阶段 4：原创视觉、声音与可读性打磨

**预计用时：** 2–3 天（12–18 小时）\\
**推荐模型：** 图像生成模型制作原创草图/素材；GPT-5.6-Terra 集成；GPT-5.6-Sol 做性能审查\\
**目标：** 在不改变已验证规则的前提下，让高速信息一眼可读。

**任务：**

1. 确定原创美术语言（建议“夜间海岸霓虹 + 扁平像素化轮廓”），制作玩家车、三类交通车、燃油、道路与 HUD 资源。
2. 添加引擎、加速、碰撞、补给、警示音与基础音量控制；所有音频使用原创或有授权资源。
3. 调整颜色、描边、阴影、屏幕震动与警示效果，确保玩家车、道路边界、燃油和危险车始终可辨识。
4. 移除开发 HUD，保留必要设置和按键提示。

**验收标准：**

- [ ] 玩家在高速时能在 0.5 秒内区分车、补给和路边界。
- [ ] 静音、低分辨率和窗口缩放时核心信息仍可用。
- [ ] 项目不包含参考游戏的任何素材或可辨识复刻元素。

**验证：** 以 720p/1080p、静音/有声各试玩一局；让试玩者截屏指出玩家、燃油和危险来源。

**依赖：** 阶段 3。

### 阶段 5：测试、平衡与 Windows 发布包

**预计用时：** 2–3 天（12–16 小时）\\
**推荐模型：** GPT-5.6-Sol（高推理）主导测试设计与疑难问题；GPT-5.6-Terra 修复与打包\\
**目标：** 形成可稳定交给他人试玩的 Windows 构建。

**任务：**

1. 为可纯逻辑验证的部分写自动检查：重开重置、燃油结束、出生车道、最小间距、难度阶段切换。
2. 做 5 分钟压力测试与至少 20 局随机种子回归；记录崩溃、卡顿、无解局和异常数值。
3. 邀请至少 3 人试玩，收集存活时长、死亡原因、公平性评分和最困惑的操作。
4. 每轮只改动少数参数，记录改前/改后结果，避免“凭感觉大改”。
5. 配置 Windows 导出、写运行说明，完成启动—单局—重开的最终冒烟测试。

**验收标准：**

- [ ] 自动检查通过，20 局回归无崩溃或阻断性状态错误。
- [ ] Windows 包在干净环境可启动并完成一局。
- [ ] 三名试玩者均能独立开始、暂停、结束与重开；主要反馈已记录。

**依赖：** 阶段 4。

## 5. 总排期与里程碑

| 里程碑 | 累计时间 | 可交付结果 | 决策点 |
|---|---:|---|---|
| 阶段 0 完成 | 第 1 天 | 可调规则表、项目基线 | Godot 环境与原创方向确认 |
| 检查点 A | 第 2–3 天 | 60 秒驾驶原型 | 操控是否值得继续 |
| 检查点 B | 第 5–7 天 | 交通与碰撞核心循环 | 公平性是否达标 |
| 检查点 C | 第 8–10 天 | 完整可玩单局 | 时长和重玩动机是否达标 |
| 阶段 4 完成 | 第 10–13 天 | 原创可读视觉与声音 | 资源不侵权、信息清晰 |
| MVP 发布候选 | 第 12–16 天 | Windows 试玩包 | 是否进入 Web/新赛道等后续迭代 |

## 6. 主要风险与应对

| 风险 | 影响 | 预防与处理 |
|---|---|---|
| 机械上太像参考游戏 | 高 | 只参考抽象玩法；使用原创世界观、资源、交通行为、数值和道路结构；必要时做知识产权审查。 |
| 交通生成造成无解局 | 高 | 固定种子回归、最小反应时间、相邻车道逃生检查、早期试玩。 |
| 操控在高速下失控 | 高 | 第一阶段就做高速换道验证；调横移、加速度和道路宽度，而非等到美术后处理。 |
| 需求膨胀 | 高 | 每一个新增系统都只能在 MVP 发布候选后评估；MVP 期间不增加赛道/改装/联网。 |
| AI 代码看似可用但 Godot API/状态有误 | 中 | 小切片运行、自动检查、每个阶段本地冒烟测试；高风险部分用 Sol 复核。 |
| 美术占用过多时间 | 中 | 先色块、后原创资源；视觉工作有 2–3 天硬上限。 |

## 7. 定义完成（Definition of Done）

- [ ] 所有阶段验收项完成，未通过项有明确的延期或取舍记录。
- [ ] Windows 构建从启动到重开完整可玩。
- [ ] 关键规则可通过配置调整，重开不会残留状态或节点。
- [ ] 至少三份试玩记录证明核心体验可理解且基本公平。
- [ ] 代码、资源和文案均为原创或具有明确授权；不包含《Road Fighter》原始内容。
